# Auditing Problem Packages

Audit the package as one judging system. Do not edit it, silently repair defects, or treat a successful compile as release evidence.

## Discover the package

Audit only the package directory or artifacts the user places in scope. If neither is provided, ask one question for the package path or relevant files and stop; do not emit a verdict or audit the plugin workspace by default.

Locate the statement, editorial, reference solution, generator, validator, build/test entrypoint, test data, and any checker or interactor. Prefer the standard `src/` plus `build/` layout, but accept an alternative layout when each role and its build command are unambiguous. A missing required role or reproducible build/test entrypoint is a blocker.

Run only safe documented build and test commands. Do not invoke cleanup targets, delete generated data, or mutate package configuration. Record each command, exit status, and relevant output as evidence.

## Audit release gates

| Gate               | Verify                                                                                                                                                               |
| ------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Completeness       | Required artifacts exist, contain no unfinished placeholders, and have one authoritative source location.                                                            |
| Statement contract | Statement input/output grammar, bounds, special cases, and samples agree with the validator and reference solution.                                                  |
| Solution contract  | Editorial matches the reference algorithm; complexity fits stated limits.                                                                                            |
| Test data          | Generator and existing tests satisfy the validator; reference outputs are generated by the reference solution; cases include boundaries and likely wrong approaches. |
| Judging            | Build and configured tests succeed; checker/interactor is required, built, and statement-compatible only when its problem type needs one.                            |

Treat a statement/validator mismatch, generator output rejected by the validator, invalid sample, absent answer-generation path, failed command, missing required tool, or unresolved placeholder as a blocker. Treat absent stress-test evidence as a warning and recommend `stress-testing`; it does not block release by itself.

## Return a release report

Return this shape, with evidence rather than assumptions:

```text
Verdict: PASS | BLOCKED

Blockers
- [artifact(s)] defect — impact. Next action: ...

Warnings
- [artifact(s)] concern — recommended follow-up.

Verified evidence
- command or inspected relationship — observed result.
```

Use `PASS` only when no blockers remain. Cite the conflicting artifacts and the exact contract difference in every finding. Recommend the relevant skill (`writing-statement`, `writing-solution`, testlib guides, `stress-testing`, or `building-problem-packages`) without changing files.

## Avoid

- Do not assume a nonstandard layout is invalid when all roles are discoverable.
- Do not claim generator coverage is strong merely because random data exists.
- Do not run a custom checker as an ordinary output comparison or expose hidden answer data in the report.
